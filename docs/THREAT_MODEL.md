# Threat model

Requirement R4 (`docs/REQUIREMENTS.md`). Scope: the system as built in this repository, deployed
by `charts/platform` on local k3d. Architecture and mechanisms are in [`DESIGN.md`](DESIGN.md);
this document says what can go wrong, what stops it (with the implementing file), what is left,
and what is not done. "Not done" items are real gaps, not plans.

## 0. The brief's four questions, answered directly

Short answers; the tables in §3 have the detail and the implementing files.

**Shared upstream credentials: what can a member do with a credential they never see?**
An admin stores one credential per upstream (e.g. the GitLab token). It is encrypted at rest
(AES-256-GCM, `crypto/secretbox.ts`, key from the Secret `urumi-env`), decrypted only inside
`callTool` for the outgoing request (`upstreams/decrypt-for-call.ts`), and never returned by any
API, log line or the dashboard (members do not even see the upstream URL). A member can therefore
only _use_ it, and only through the gateway: they can call the tools their tool permissions allow
(ADR 008: members are read-only by default), `/mcp` calls are rate-limited per key and per user, and
every call is written to `audit_log` under their own user id. What they **can** do is anything
those permitted tools can do with the upstream account's rights — the credential's scope is the
real limit, so admins should give each upstream the narrowest token that works. They cannot copy
the credential, use it outside the gateway, or call a tool they were not granted (`FORBIDDEN`,
audited `denied`).

**Why client tokens are not passed through to upstream servers.**
A client's API key or OAuth token proves _who the caller is to the gateway_; it is checked
(SHA-256 lookup) and consumed at `/mcp`, and the outgoing request carries only the upstream's own
stored credential (`credentialHeaders` in `upstreams/decrypt-for-call.ts`). Passing the client's
token on would (1) hand a gateway credential to every upstream, so a malicious or compromised
upstream could replay it against the gateway or against other upstreams, (2) be meaningless to the
upstream, which never issued it (the MCP spec forbids this "token passthrough"), and (3) bypass the
gateway's permission, rate-limit and audit checks, which only work if the gateway is the single
place that decides. Tokens are audience-bound to the gateway (OAuth `resource`, ADR 013).

**Untrusted upstreams: tool descriptions written to manipulate the model.**
Everything an upstream returns is treated as data. Descriptions are stripped of control and bidi
characters and capped at 500 characters; tool names are sanitised and prefixed with the server
slug, so an upstream cannot impersonate another server's tool (`core/registry.ts`, `naming.ts`).
Descriptions are sent only as tool definitions, never in the system prompt, and the system prompt
tells the model that tool descriptions and results are untrusted. Upstream `instructions` are
never forwarded. Even if the model is fooled, it can only call tools the _logged-in user_ is
allowed to call, at most 8 rounds per message, and each call is audited. Remaining risk: an admin's
chat (or a member with write grants) can still be tricked into a write without confirmation (§4).

**What one team member can do to another.**
Very little. A member cannot see or revoke another member's API keys, cannot read another member's
audit rows (the API forces the filter to their own id), cannot change roles, users, upstreams or
permissions (`requireAdmin`), and has their own `/mcp` rate-limit bucket. Chat history is not stored on
the server. What they _can_ affect: data in the shared upstream accounts (e.g. if granted a write
tool on the store, they can change an order another member also sees) — but every such call is
audited under their name. An admin can do more (create/disable users, revoke anyone's keys, change
permissions) but cannot demote or disable themselves, and the last admin cannot be removed.

## 2. Trust boundaries

```mermaid
flowchart LR
  subgraph internet["Untrusted: internet / user devices"]
    browser["Browser"]
    mcpc["External MCP client"]
    gitlab["GitLab MCP (third party)"]
    anthropic["Claude API"]
  end
  subgraph cluster["Cluster namespace urumi"]
    traefik["Traefik Ingress"]
    subgraph trusted["Trusted code"]
      gw["gateway"]
      dash["dashboard (static)"]
      job["bootstrap Job"]
    end
    subgraph semi["Our upstreams (trusted code, untrusted output)"]
      woo["woo-mcp"]
      every["server-everything"]
    end
    pg[("Postgres")]
    wp["WordPress / WooCommerce"]
    maria[("MariaDB")]
    secrets[["K8s Secrets"]]
  end

  browser -- "B1: cookie session" --> traefik
  mcpc -- "B1: Bearer key" --> traefik
  traefik --> gw
  traefik --> dash
  traefik -- "storefront, wp-admin" --> wp
  gw -- "B2: tool calls, results are data" --> woo
  gw -- "B2" --> every
  gw -- "B3: internet, PAT" --> gitlab
  gw -- "B4: prompts + tool results" --> anthropic
  gw --> pg
  woo -- "App Password" --> wp
  wp --> maria
  secrets -. env .-> gw
  secrets -. env .-> woo
  job -. writes .-> secrets
```

- **B1** Clients → Ingress → gateway: every request is authenticated (cookie or bearer key) and
  validated (zod, strict schemas, `packages/contracts/src/api.ts`).
- **B2/B3** gateway → upstreams: admin-chosen URLs; everything that comes back (tool names,
  descriptions, schemas, results, errors) is untrusted data.
- **B4** gateway → Claude: the model's tool calls are untrusted requests, executed with the
  signed-in user's rights.
- Admins are trusted to register upstreams but not to reach the cluster network through them
  (SSRF).

### 3.6 Denial of service

| Limit                                             | Exists?                                                                                   | Where                        |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------- |
| Login attempts                                    | yes: 10 / email, 30 failures / IP, per 15 min, in memory **per replica** (2× with 2)      | `auth/login-limiter.ts`      |
| Chat requests                                     | yes: 20 / user / sliding minute → 429, per replica                                        | `chat/rate-limit.ts`         |
| Chat cost per request                             | yes: ≤ 8 tool rounds, 1024 output tokens per turn, 64 KB history, 60 s Anthropic deadline | `chat/service.ts`            |
| `/mcp` body                                       | yes: 1 MB; unauthenticated requests rejected before the body is read                      | `mcp/endpoint.ts`            |
| woo-mcp body / request time                       | yes: 1 MB, 30 s server request timeout                                                    | `apps/woo-mcp/src/server.ts` |
| Upstream timeouts and payload caps                | yes                                                                                       | see 3.5                      |
| `/mcp` request rate per key and per user          | yes: Postgres token buckets shared by replicas → 429 + Retry-After, audited (ADR 010)     | `ratelimit/bucket.ts`        |
| OAuth DCR / authorize / token per IP (ADR 013)    | yes: Postgres buckets; registration also capped globally; unused clients pruned after 1 d | `oauth/routes.ts`            |
| `/api/*` request rate (other than login and chat) | **no**                                                                                    | —                            |
| Concurrent calls per user or per upstream         | **no**                                                                                    | —                            |
| Resource limits on every container                | yes, enforced by `tests/infra/chart-checks.sh`                                            | `values.yaml`                |

Residual: a valid key is held to its bucket (default 120/min, burst 60; per user 240/min,
burst 120), but each refused request still costs two Postgres statements and one audit row, so a
flood with a valid key still loads Postgres (attributable: every refusal is audited with the key).
The login throttle and chat limit are per replica and reset on restart.

(`apps/gateway/src/oauth/`). Tested in `test/oauth*.test.ts` and e2e D13.

## 4. Summary of open risks

1. Prompt injection can drive write tools in chat without confirmation — for admins and users
   with a write grant; members have no write tools by default (ADR 008) (3.5).
2. SSRF: the allow-list is exact in-cluster hosts by default, but a wildcard override would admit
   every matching Service (3.4).
3. Upstream response bodies are buffered before the 256 KB cap is applied (3.5).
4. `/mcp` is rate limited per key and per user (ADR 010), but the login throttle and chat limit
   are per replica (3.6); no key expiry (3.1).
5. Audit log is mutable by the gateway's DB role; admin actions are not audited (3.2, 3.3).
6. Secrets are plain Kubernetes Secrets; no encryption at rest or rotation tooling (3.4).
7. Egress to the public internet on 80/443 is open for the gateway, WordPress and the bootstrap
   Job (no FQDN filtering); in-namespace traffic is default-deny (3.7, ADR 009).
8. OAuth (ADR 013): consent phishing is mitigated (unverified-name warning, redirect host shown,
   Connected apps, audit by client) but not prevented; tokens are bearer tokens (no DPoP); the
   local issuer is plain HTTP (3.8).
9. Hosted MCP servers (ADR 014): the image allow-list is enforced by the gateway, not by an
   admission controller, and images are not signature-verified or scanned; a hosted server created
   with egress can send what it receives to the internet (3.9).
10. Multiple stores (ADR 015): the gateway holds cluster-scoped namespace rights, confined to
    `store-*` namespaces by an admission policy; a stolen gateway token can delete every store's
    data; stores reach the internet on 80/443 (3.10).
